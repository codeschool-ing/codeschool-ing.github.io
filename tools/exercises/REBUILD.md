# Rebuild prompt — the exercise pipeline in Go

A draft of the single prompt that rebuilds this tool from scratch, in Go, inheriting no code.
Written from [`RULES.md`](RULES.md), which remains the source: if the two diverge, that one
wins and this one gets updated.

**Deliberately left out:** this school's course catalogue, this API account's cost figures and
the JavaScript implementation's file names. They belong to this instance, not to the problem.

**How to use it:** attach the three files listed below and copy everything under the rule into
a fresh session. The text alone rebuilds the architecture and the process; the attachments are
what stops the rebuild paying again for what this project has already paid for.

### The three attachments, and what happens without each one

| attachment | file | role | without it |
| --- | --- | --- | --- |
| the corpus | `exercises-python.json` (48 exercises, 81 KB) | calibration of the mechanical checks | they are born noisy, whoever implements them loosens the thresholds to silence the noise, and the free layer comes to exist while flagging nothing — the worst possible outcome |
| the prompts in full | `prompts.md` (11 prompts, ~6,700 words) | the accumulated authoring and critique text | the "What the authoring prompt has to require" section is ~490 words and is a summary. What disappears in a summary are the worked cases, and an abstract rule is obeyed sometimes while a concrete case is obeyed |
| the round history | `history.json` | the verdict's baseline | the first rounds print "first round of this course" and do not answer whether the tool improved, which is the question the verdict exists to answer |

`prompts.md` is generated by `node exercises.mjs --prompts` and versioned. Two tests keep it
honest: one checks that the file matches the prompts in the code, and another sweeps the code
for an exported prompt that is not in the attachment — the failure that matters is not the
stale file, it is the new prompt the pipeline starts using without anyone remembering to
register it.

About the first one: the exercises have **two roles**, and only one of them belongs to this
instance. As *content*, they belong to a specific course and are of no interest to anyone else.
As a *corpus*, they are the only defence against a false positive in a mechanical check, and
that belongs to the problem. Attach any set of exercises a person has reviewed and considered
good — the ones in this codebase will do, your own will do better. What will not do is none.

---

## What to build

A command-line program, in Go, that **generates, verifies and critiques self-gradable
programming exercises** from a course syllabus, using a frontier language model with structured
output.

It is not a content generator with optional verification. It is **a rejection funnel** that
happens to also write. Writing is the cheap part and is already solved; the entire value is in
discovering, before a student wastes their time, that the exercise does not measure what it
promises.

The program runs across dozens of courses and hundreds of topics, and every call costs money.
Two consequences govern the whole design: **whatever can be checked by computation must never
cost a call**, and **every round has to say by itself whether the tool improved**.

## The real problem, so you do not optimise the wrong thing

A model writes plausible exercises very easily. Almost all of them have a defect that only
shows up when somebody tries to answer:

- the correct option is the longest one, or the only one with a caveat, or the only one without
  "sempre" — and a student who never studied the subject gets it right out of exam habit;
- the statement promises to measure a concept and there is a solution that ignores the concept
  and passes every test case;
- the hint does not point at what to examine: it hands over the decision criterion already
  applied to the case;
- the key is wrong in a way only execution reveals;
- the topic's natural tool produces a different result from the key, so the exercise **punishes
  whoever studied**.

None of that shows up reading the exercise in good faith, which is exactly what a model does
when you ask it to "assess the quality". That is why the program does not ask for an opinion:
it measures behaviour and computes what can be computed.

## Non-negotiable principles

These five came from defects that cost money. If any of them gets in the way of the
implementation, solve it another way — do not remove them.

1. **Free before paid.** A check that is arithmetic runs first, always, and fails without
   calling the API. A rule that becomes computation starts being obeyed; a rule that stays only
   in the prompt is obeyed sometimes.
2. **Proof before judgement.** If it can be executed and compared, execute and compare. Opinion
   is the last resort, not the first.
3. **Blind oracle.** Whoever verifies does not see the key. The reference solution is written
   without seeing the test cases; the probe answers without seeing what is marked correct.
   Blind agreement is evidence; agreement from someone who saw the answer is nothing.
4. **A probe instead of a score.** Never ask for "give it a score from 1 to 5". Ask for an
   observable behaviour — *answer this question*, *solve it with this hint* — and compare with
   the key.
5. **Only ask a probe what it is able to refuse.** A probe forced to answer always answers, and
   becomes opinion under another name. See the guessing probe's case further down: it is the
   most expensive rule in this codebase.

## Input

A course syllabus: identifier, name, description, audience, and an **ordered list of topics**.
The order is a semantic constraint, not decoration — an exercise for topic N may only require
what topics 1..N have already taught.

Format: whatever is convenient (JSON is enough). The program lists the available courses and
accepts one of them by identifier, or an already-generated exercise file, to resume without
regenerating. Resuming is what makes it cheap to fix a key by hand and re-check.

## The seven exercise types

They all share: a declared topic, a difficulty, a statement and a **socratic hint**.

| type | the student does | how it is graded |
| --- | --- | --- |
| `code` | completes a skeleton | runs it against test cases, compares stdout |
| `expected-output` | types what the snippet prints | runs the snippet, compares byte for byte |
| `quiz` | picks one option | exactly 1 correct |
| `multiple-choice` | picks several | **exact set**: getting one item wrong fails everything |
| `ordering` | orders shuffled steps | exact sequence |
| `matching` | joins columns | exact set of pairs, with distractors on the right |
| `expression-answer` | writes a mathematical expression | symbolic equivalence via a CAS |

Every option carries a `why`, which is **post-answer feedback** and never a visible tell.

Two warnings with a history:

- **`ordering` should not go into automatic generation.** In this codebase six were generated
  across four rounds, zero approved, with a different reason every time. The type is valid for
  hand-written content, where an author proves the trap exists. Implement it, validate it, and
  leave it out of the list of generatable types until a hand-written one passes the critic
  twice in a row.
- **`multiple-choice` is structurally fragile.** With exact-set grading, five options are five
  chances to be wrong instead of one, and a single debatable item fails the whole exercise.
  Measure the approval rate by type from the first round. If it stays below half the `quiz`
  rate for three rounds, require that **every option be verifiable** rather than judged, or
  take the type out of generation.

## Layer 1 — the mechanical check, for free

It runs first, always, with no network. Every item below was born of a real defect; the "why"
is what lets you negotiate thresholds without destroying the rule.

**Structural**

- `quiz` has exactly 1 correct option. `multiple-choice` has 2 or more and never all of them.
- Every option has text and a `why`; a type's fields do not appear in another type.
- `matching`: 4 to 6 pairs, no repeated item in either column (a repeat = more than one key),
  plus 1 or 2 distractors on the right, distinct from the correct right-hand items. With no
  distractor, N against N makes the last pair come out by elimination.
- `matching`: the **statement** has to warn that items are left over. Whoever does not know that
  tries to fit them all and forces a wrong pairing. The hint is no good for that warning — not
  every student opens it.
- `ordering`: 4 to 7 items, none repeated, with a **trap declared** by the author (which
  neighbouring pair the student inverts, and why inverting breaks it). No item may contain an
  anaphor — "esse", "esta", "anterior" — because "executa **esse** bytecode" pins the position
  by the text, not by understanding.
- `expression-answer`: the variable used in the check has to be among those declared.

**Form tells** — all in `quiz` and `multiple-choice`, all answering the same question: *can a
clever student who did not study get it right on form alone?*

| check | why it exists |
| --- | --- |
| every correct option noticeably longer than every wrong one (>25%), or the reverse | the author elaborates the right one and dispatches the wrong ones |
| an absolute ("sempre", "nunca", "apenas", "impossível") present on one side only | an exam-taker discards an absolute out of habit, without reading the merits |
| every correct option echoing far more of the statement's vocabulary than any wrong one | word matching settles the question |
| a **technical identifier** from the statement present in exactly one option, the correct one | word counting does not catch this: the echo sums to 1 and passes any threshold |
| all the correct ones qualified and no wrong one qualified | "qualified = right" is as good a heuristic as "absolute = wrong" |
| an **adverb of uncertainty** in exactly one option, the correct one | the single-correct-option case, which the previous check does not cover |
| in `multiple-choice`: marking the hedged ones and discarding the absolute ones produces **the exact key** | it is the exam heuristic simulated, and it measures what decides the grade |
| the hint stating **how many** options are false | it turns into label triage: the student looks for the two in the named category and marks the rest |
| two or more hint words present in exactly one option, the correct one | the hint became an arrow; a textual match, not a conceptual one |

**Thresholds already calibrated.** All of them were tuned against a hand-reviewed corpus until
they flagged no good exercise. Each one has an obvious value that **is wrong** — if you pick the
obvious one, you will harvest the false positive that has already been paid for here.

| check | threshold | the obvious value, and why it errs |
| --- | --- | --- |
| length | shortest correct > longest wrong × 1.25 | with no margin, any natural variation in wording flags |
| lexical echo of the statement | lowest correct ≥ 3 words **and** ≥ highest wrong **+ 3** | the obvious value is +1, and +1 flagged two good exercises — a one-word advantage is noise |
| technical identifier | only an acronym (two or more capitals) or a term with a digit | accepting any word flags common verbs: "executar", "marca", "repetir" |
| hint words | a bundle of **2 or more** pointing at the same option | one word is coincidence: "outro", "valor" and "saída" landed in a single option, by chance, in 3 of 48 |
| absolute / hedging by group | **strict** separation: all on one side, none on the other, with ≥2 on each side | a majority is not enough; it flags ordinary prose |
| exam heuristic simulated | only with **2 correct options or more** | with a single correct one, the simulated set matches by chance far too easily |
| adverb of uncertainty | exactly 1 protected option, ≥4 options in total | too wide a vocabulary knocks out a good exercise — see caution 3 below |
| syntactic mould | ≥2 wrong options with the same **first two words**, and no correct one like that | 3 looks safer, but the case that motivated it had exactly 2 |
| a hint counting how many are wrong | a number and a truth word less than ~60 characters apart | looking for the two anywhere in the text flags an unrelated sentence |

Calibrate in **both directions**: no false positives in the corpus, and one test per rule
proving it still fires on the real case that motivated it. Calibrating in one direction only
produces a rule that flags nothing, and nobody notices.

Four calibration cautions, each paid for with a real false positive:

1. **Demand strict separation** in the group checks (all on one side, none on the other). A
   majority is not enough; it flags ordinary prose.
2. **A technical identifier is an acronym or a term with a digit.** The version that accepted
   any word flagged common verbs in good exercises.
3. **Separate "hedge" from "contrastive connective".** For the adverb-of-uncertainty check use a
   narrow vocabulary — only what softens a *claim* ("provavelmente", "em geral", "tende a").
   "Enquanto" and "mas" are ordinary explanatory prose and knock out a good exercise.
4. **One word in common between the hint and an option is coincidence**; demand a bundle of two
   or more pointing at the same option. And do not use the statement as the source for that
   test: it shares vocabulary with every option by construction.

## Layer 2 — execution, proof instead of opinion

- **`expected-output`** runs the snippet and compares byte for byte with the key. It is the
  funnel's strongest type: a semantic error becomes a deterministic failure, no discussion.
- **`code`** asks the model for a **reference solution written without seeing the test cases**,
  and runs that solution against them. Agreeing blind is evidence that the statement and the
  cases describe the same thing. Disagreeing means one of the two is wrong, and the verifier
  does not guess which — it fails and shows both sides.
- **`expression-answer`** recomputes the key in a CAS from a declared source. An exercise that
  declares "no check" **fails**: with no recomputation nobody verified anything, and approving
  it would stamp a quality mark on something unchecked.
- **Never store as a reference solution something written by someone who saw the cases.** That
  converts independent verification into self-verification, and the program starts reporting
  "ok" without anything having been checked.
- **A missing environment exits with its own error code and never fails content.** An
  interpreter off the PATH has already become "eight exercises failed" and sent someone hunting
  for a defect in the content. An execution error arrives with an empty stderr: never swallow
  the cause.

If you support SQL, note that **the output format is a contract, not a choice**. An in-memory
database created empty on every run; the setup travels with the exercise; the format — header,
separator, how `NULL` and each column type print — is pinned in the authoring prompt. Without
it the generator invents one per exercise and the byte-for-byte comparison fails a correct key.
Turn foreign keys on explicitly, and require an `ORDER BY` on every query, or the key comes to
depend on the order the engine happened to return.

Running model-generated code is the program's dangerous point. A timeout per case, no network,
and a clear warning in the documentation that volume is run in a disposable container.

## Layer 3 — critique: probes and one judge

**Probes** (behaviour, worth more):

- **The blind probe** answers the question without seeing which option is marked. If it diverged
  from the key, somebody is wrong.
- **The blind pair probe**, for `matching`, and its shape is the lesson. Do not ask "which one
  is the pair" and compare with the key: a competent model, forced to choose one pairing,
  chooses the intended one, and it approved three known-bad exercises. Ask **for each left item,
  which right items defend themselves as its pair** — the multiplicity becomes the answer being
  asked for, and a left item accepting two defensible pairs is the ambiguity you are hunting.
- **The hint probe** tries to solve the exercise seeing the statement, **everything the student
  sees** and the hint — never the key. The "everything the student sees" is literal and was
  learned expensively: when the probe received only the statement and the hint, on an
  `expected-output` it received "what does this snippet print?" **without the snippet**, and
  approved everything for want of any way to disagree.

Two rules the probes cost money to learn:

- **The response format must not destroy the information being sought.** Asking "which one" when
  the question is "how many" always returns one, and the instrument passes for working.
- **Caution written inside the instrument becomes blindness of the instrument.** A prompt of
  mine said "when in doubt between listing and not listing, do not list" — which suppresses
  exactly what the probe measures. When you ask someone to look for a defect, you do not also
  ask them to err on the side of not finding one.

And a coverage rule: **every type with a key has to have a blind probe.** Partial instrument
coverage is worse than none, because the report does not distinguish "passed" from "was not
measured".

**The probe that must not exist.** There was a third one, the "guessing" probe: it answered
forbidden to use knowledge of the subject, with exam heuristics only, to detect exercises
answerable on form. It hit the key **9 times out of 9** and failed a whole course.

A model does not suspend what it knows. It fabricates a form-based justification for the answer
it already believes in. In one case it noticed an absolute in the **correct** option, argued
that it "came qualified", and included it anyway — rationalisation towards the target, not
prediction. **Do not implement that probe.** Every heuristic it tried to apply belongs in
layer 1's mechanical checks, where they are arithmetic and hold no opinion.

**A judge** (one judgement pass, with structured output, for what a probe cannot reach: an
ambiguous statement, a debatable key, an implausible distractor, a scope that does not match
the topic). Three requirements:

- **The judge needs to see the exercise, not its serialisation.** Showing escaped JSON produced
  a whole round of identical rejections complaining of "string notation with quotes" — the
  judge was judging the prompt's formatting.
- **The judge needs to know the school's conventions**, or it reports design decisions as
  defects: that `multiple-choice` has several correct options on purpose, that the comparison
  ignores trailing whitespace, that the `why` is post-answer feedback.
- **The judge does not judge whether the hint gives too much away.** That belongs to the probe.
  Opinion about hints always errs the same way, because every useful hint narrows the field;
  under the ruler "does this change who passes?", no hint survives. In one round, 10 of 16
  rejections were the judge finding hints generous, and not one came from the probe. The judge
  only reports a **wrong** hint: a false statement, pointing at the wrong place, contradicting
  the statement.

**The severity ruler: "does this change who passes?"** Getting it right by elimination without
knowing the subject is high severity. Low severity only for what changes nobody's result.

**Unjudged never becomes approved.** If the critique pass fails, retry once; if it fails again,
fail the exercise. A misread response becoming "low severity" makes the exercise pass without
having been assessed.

## Layer 4 — rewriting what fell

The rejected exercise is not discarded: it goes back to the author **with the report in hand**
and passes through the whole funnel again. It has already paid for a generation and a critique,
and the defect came named.

The risk is **teaching to the test**: rewriting until the judge approves optimises against the
judge, and a judge has biases. Four locks, none removable without a replacement:

1. The rewrite goes back through the **whole** funnel, not only through the critique. A
   mechanical check does not change its mind or get tired.
2. The blind probe **does not read the critique**. There is no wording that pleases it.
3. **One lap by default**, configurable, with the cost per approved exercise visible at the end.
4. **Type and topic are pinned.** Swapping a hard type for an easy one would solve the rejection
   and falsify the two measures that keep the generator honest: topic coverage and rate by type.
   A rewrite that changes either is refused before entering the funnel.

Also refuse a rewrite identical to the original, and an empty response. And tell the author, in
the prompt, that **the defect is fact and the suggested fix is a guess** — whoever reported the
defect did not write the exercise, and there has already been a case of a wrong suggestion with
a right defect.

## The progress verdict

At the end of every complete cycle, the program writes a line into a history and prints a
three-state verdict: **IMPROVED**, **STALLED**, **WORSE**.

The number that decides is **not the approval rate**. It moves with the course, with the topic
and with the difficulty that came up, and it rises by itself if the generator turns timid. What
measures the tool is the **division of labour**:

> how many defects were caught by computation, for free, against how many only appeared after
> paying the API.

Every rule that becomes arithmetic pushes a defect from one column to the other. If that
proportion does not move across rounds, the rounds are fixing content, not the tool.

Record per round: course, topics, generated, failed by layer, approved, rewritten, rescued,
rejection causes by dimension, and total cost. Compare **only with the previous round of the
same course** — different courses have different difficulty, and comparing two would measure the
subject. Also show the **cost per approved exercise**, which is the only way to know whether the
rewrite stage pays for itself; if it rises by more than a quarter, say so glued to the verdict,
and not on a line that can go unread.

Two traps in this bookkeeping, both paid for:

- **A rescue does not enter the verdict's rate.** Count the **first pass** only, and show the
  rescued ones on a separate line labelled as bought approval. Adding the two printed
  "IMPROVED +34 pp" over a generator that had not moved a point.
- **A missing datum must not turn into silence.** With no baseline for a dimension, print the
  number and say there is nothing to compare it with. An instrument that falls silent when a
  datum is missing is worse than a missing one: it passes for working.

## What the authoring prompt has to require

**This section is a summary, and the real prompt is attached.** It is ~490 words here against
~2,800 there, and the difference is not padding: it is the worked cases. "The hint must not
offer a criterion that contradicts the key" is obeyed sometimes; the same thing with the case
attached — *the hint told the student to check whether the statement promises something between
tools, suggesting that a promise between tools is true, and one of the wrong options was
precisely a promise between tools* — is obeyed. **Use the attachment as the text and this
section as an index of what may not be missing from it.**

Beyond the rules already cited:

- **Topic order is a constraint.** Before settling an exercise, list what it requires and check
  each item against the topic's position. Origin: an "installation and first script" exercise
  that required string manipulation, a conditional and formatting — it passed every test case,
  which is precisely why the critique exists.

  Better than the rule: **cut the syllabus.** Give the generator only the topics up to the one
  it is writing for. It reached forward because it could see forward; taking the later topics
  out of sight took `target` from 3 rejections to 1 and raised the first pass from 33% to 50%.
  You do not ask someone to ignore what they are reading.
- **The statement specifies the required output**, because the comparison is exact: whether
  there is text besides the value, which decimal separator, whether there is a trailing space.
  The student does not see the test cases and cannot discover the contract from them.
- **`code`, four questions before closing it:**
  1. Is there a solution that **ignores the topic** and passes every case? (Hardcoding a fixed
     format has already passed 5 of 5 in an exercise about a default argument.)
  2. Does the topic's **natural tool** produce your key? (An alphabetical tie-break in a topic
     whose tool breaks ties by insertion order punishes whoever studied.)
  3. If the topic is performance, does **any case separate the classes**? (Three-element cases
     approve the nested loop just like the linear solution.)
  4. Is the difficulty in the topic or in **reading the input**? (An explicit separator invites
     a naive split that breaks on an empty line and fails whoever had mastered the subject.)
- **`expected-output`: the hint never tells the student to run the snippet.** In every other
  type "run it and observe" is a good socratic hint; here the answer *is* the output.
- **The hint points at where to look, not at how to decide.** "Consider what a specification
  standardises" points; "check whether the promise is about the artefact or about the tool"
  decides — the two named categories are the two in contention, and all that is left for the
  student is to match vocabulary.
- **After writing the hint, apply it to every option** and check that the result matches the
  key. A hint that offers a criterion contradicting the key is the most expensive defect in the
  set: it fails exactly those who trust the school's guidance.
- **`matching`: the right column describes observable behaviour**, it never translates the name
  on the left — translating measures English, not the topic. And the distractor has to **compete
  with the hardest pair**: one that is discarded at a glance changes nothing, because the hard
  pair still comes out by elimination. Test every distractor against **all** the left items.
- **Level the tone between correct and wrong options.** When writing a correct one you want to
  be exact, and exactness sounds like a caveat; when writing a wrong one you want it to be
  false, and falsehood sounds categorical. If the correct ones came out nuanced and the wrong
  ones categorical, the student gets it right on tone.

And one observation that should temper your urge to write more prose: **a long rule in a prompt
is obeyed sometimes; a rule that becomes a mechanical check starts being obeyed.** In a late
round of this codebase, almost no rejection brought a new cause — they all violated rules
already written. When you find a repeatable defect, prefer converting it into computation over
adding a paragraph.

## Operational rules

- **Account for the cost before returning on an error.** A truncated or refused call is billed
  all the same. A generation that blew the output limit produced zero exercises and an empty
  cost report — silent spending is worse than high spending.
- **The output limit covers thinking and answer together.** With adaptive thinking, a batch that
  fitted at three topics does not fit at six. On blowing it, **halve the batch and redo it**
  instead of losing everything.
- **A failure never overwrites what worked.** Generating zero exercises has already renamed the
  good file and written an empty one over it. Preserve the previous version before writing, and
  exit with an error rather than write an empty file.
- **Generating by range accumulates, it never replaces.** Support producing a course in pieces,
  and make writing preserve the exercises of topics outside the range. Otherwise there is no way
  to advance through a long course, and every round covers the same first topics — which is what
  happened here for thirteen rounds.
- **The result must not depend on who answered first.** Concurrent calls return in input order.
  Verify that running with one simultaneous call and with eight produces identical output.
- **The output identifies the exercise, not the progress.** With parallelism the results finish
  out of order, and a completion counter makes it impossible to cross a finding with the line in
  the file — which is exactly the work of whoever triages the round.
- **Content is versioned; a round's derivatives are not.** The exercise file cost review to
  exist; the intermediates are remade by running again.
- **Keep the paid rejections.** They are the second corpus, and they measure reach: whether a
  new rule would have caught the defect you paid for. Do not let each round overwrite the
  previous one's rejections — here, of twelve paid rounds, one round's rejections survived.
- **A human reader.** Offer a mode that prints the exercises in readable form. Review by a
  person is this pipeline's only external signal, and nobody reviews JSON.
- **The API key in an environment variable**, never in the repository.

## Tests, before anything that costs money

A test target that runs in seconds and **does not touch the network**:

- **The attached corpus** — exercises reviewed by a person, about which **no mechanical check
  may complain**. It is the defence against false positives, and it is essential: almost every
  layer-1 check was born too eager and needed a threshold. Without a corpus you discover that by
  paying, and the way you discover it is bad — the noisy layer annoys someone, they loosen the
  thresholds, and it comes to exist while flagging nothing.
- **Every check also keeps the real case that motivated it** and a test that it still fires on
  it. Calibrating in one direction only produces a rule that flags nothing.
- **The funnel's bookkeeping runs end to end against fake functions.** It is the point where an
  error does not show up in the output: a rescue counted as a rejection, or a rejection counted
  twice, produces a plausible and false report at the end of a round that cost money. Isolate
  that logic from the network calls for exactly this reason.

## Shape of the Go program

- A single binary with subcommands, the standard library wherever possible. `flag` is enough;
  do not bring in a CLI framework.
- One package per responsibility: catalogue, types and checks, generation, execution, critique,
  rewriting, funnel bookkeeping, history, model client. The funnel bookkeeping imports nothing
  network-related.
- Concurrency with a concurrent map that **preserves input order** — indexed results, not an
  arrival channel.
- `os/exec` with `context.WithTimeout` per test case. Never inherit the parent process's stdin.
- Structured model output with a declared schema; required fields are genuinely required, or the
  model omits whatever is inconvenient and the mechanical check fails everything afterwards — a
  defect that only shows up after paying.
- Types: a single `Exercise` with the fields of all seven types and per-type validation. A
  schema per type would multiply the calls for no gain.
- Errors with context, no `panic` outside a programming error.

## What stays open, and is not an oversight

- **Deduplication between neighbouring topics** does not exist yet.
- **An out-of-place category and exotic plausibility** — wrong options that invent a strange
  mechanism while the correct ones are sober — are still prose and judgement. Mechanising them
  requires measuring semantics, not text.
- **External calibration is this pipeline's only non-self-referential signal.** Everything else
  is the same model judging itself; execution anchors what is deterministic and the probes
  measure behaviour, but "is this exercise worth a student's time?" has no automatic answer.
  Record every human review with a date, a scope and its limits — and treat agreement as an
  absence of disaster, not as proof of precision, because agreeing with a critique is easier
  than disagreeing.
